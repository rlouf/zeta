# Zeta conformance vectors

Golden test data for shared Zeta formats. Third-party implementations can
consume these files directly. The Python and Rust suites read the same files.

## `ipc/messages/valid/*.json`

Each file contains one valid JSON-RPC message and a trailing newline. A
conforming implementation must accept every file. Parsing, serializing, and
parsing the typed message again must produce the same typed value. Serialized
output must be compact valid JSON. Readers may discard unknown members and
normalize absent `params` to `{}`, so exact source-value preservation is not a
conformance requirement.

The set covers requests, notifications, success responses, error responses,
string and integer ids, absent and object parameters, `null` results, Unicode,
initialization, fixed methods, direct provider methods, and unknown top-level
members. Syntactic validity does not grant method authority; the session
vectors exercise role and connection-state rules.

## `ipc/messages/invalid/*.json` and `*.reason.txt`

Each `.json` file contains a value that the profile or one fixed protocol
method must reject. Its sibling reason file has this format:

1. The JSON-RPC error code that applies when a response is permitted.
2. A stable fixture rule name for local diagnostics.
3. A short explanation with the relevant specification section.

An invalid response or notification produces a local violation and no reply,
but its reason file still records the error code for consistent validation.

## `ipc/sessions/*.jsonl`

Each file is one scripted connection. Every line is a JSON-RPC message with an
extra `_dir` member:

- `"peer_to_runtime"` means that the peer sends the message.
- `"runtime_to_peer"` means that the runtime sends the message.

Strip `_dir` before message validation. `source-provider.jsonl` covers durable
event publication, a direct provider request, equal ids open in opposite
directions, source responses resolved out of order, ping, and orderly shutdown.
`client.jsonl` covers queries, session submission, a committed-event
notification, cancellation, and shutdown. `capability-provider.jsonl` covers
provider initialization, a direct capability request with its execution
context, the matching result, and orderly shutdown.

## `addresses/vectors.json`

Inputs with their expected `b3:` addresses for identity domains defined by the
substrate specification. The `content` set uses plain, undomained BLAKE3 of the
input bytes. Each vector gives the
input bytes as UTF-8 text (`input_utf8`) or base64 (`input_base64`)
and the expected address. An implementation's output must match
byte-for-byte, including for the empty input.

## `substrate/encoding.json`

Identity-bearing JSON values with their exact canonical UTF-8 text.
Python 3.11 generated this file before the Phase 1.5 mint changed. The
vectors include Unicode ordering, nested and null-heavy values, float
notation boundaries, and the accepted i64/u64 integer edges. The rules
are normative in `spec/substrate-v0.md` §2.

## `substrate/b3-addresses.json`

Objects and derivations generated by the current Python substrate.
Each entry pins the complete fields, canonical UTF-8 bytes, and active
object-domain or derivation-domain address. The root links two active
leaves, so both language suites verify one small Merkle DAG.

## `journal/chain.json`

Complete backend-neutral events with their exact canonical payload bytes,
domainless payload addresses, versioned chain arrays, predecessor addresses,
and Chain-domain entry addresses. The ordered cases cover null-heavy genesis,
literal Unicode, every optional event field, and the substrate numeric edges.

## `journal/operations.json`

A deterministic journal transcript generated from the pre-change Python
memory store. It pins successful appends, id-first and idempotency-key
deduplication, cursor-ordered filters, literal prefix behavior, missing causal
parents, cycle termination, and the final journal head. It contains no storage
schema or payload-placement assumptions.

## `authoring/agents.json`

The versioned `zeta-authoring-v1` document freezes the complete portable
authoring boundary. Its sections cover agent parsing and typed locks; sorted
Draft 2020-12 event schemas; returned-schema definition rewriting; prompt
validation and rendering; flat and `SKILL.md` skills; language-neutral
connector descriptions; semantic diagnostics; and exact project/execution
manifest identities.

Python and Rust recompute the portable parser, event, returned-schema, prompt,
and skill cases. Cases marked `language_neutral_contract` intentionally replace
Python snapshot behavior and are checked directly in Rust: equal event merges,
strict unknown returned events, caller-supplied skill fallback names,
connector implementation fingerprints without commands, and version 1
manifests. The expected declarations contain no source path; paths in parser
cases only let Python exercise its loader while Rust parses the supplied bytes.

## `agent/prompts.json`

The version 2 document contains eight prompts generated by the Python runtime
with a fixed date and working directory. Each case contains the ordered prompt
components, model input, request payload, substrate objects, derivations, and
their exact addresses. `ModelInput` no longer carries `selected_url`; endpoint
selection belongs to `ModelRequest.url`. The cases cover minimal and repaired
tool histories, the fifty-event history boundary, private trace filtering,
authorized content ordering, structural trimming, and drop-oldest compaction.

## `agent/invocations.json`

The version 2 document contains twelve deterministic agent runs generated by
the Python runtime. Scripted model and tool results cover streaming, tool
execution and rejection, native and Codex tool presentations, effect ordering,
duplicate calls, event controls, cancellation boundaries, and content query,
transform, and finish operations. Step evidence uses `check_abort`, and the
explicit maximum-call case pins `max_model_calls` as its stop reason. Each case
also pins journal drafts, observations, control requests, step order, and the
trace objects and derivations produced by the run.

## `agent/models.json`

Chat Completions and Responses requests with their exact headers and payloads,
incremental SSE chunks, normalized model output, and stable failure results.
The cases cover fragmented events, reasoning, tool calls, usage, replay items,
provider errors, Codex authentication headers, and stream timeout settings.

## `agent/tools.json`

Nine native tool declarations and eleven deterministic calls. The cases cover
file reads and writes, directory listings, exact edits, patches, text and
structural search, bounded shell execution, URL safety checks, and injected web
search results.

## `dispatch/runtime.json`

Implementation-neutral durable-runtime rules generated by the Python harness.
The document pins deterministic queue, attempt, run, request-handle, and
idempotency identities; exhaustive queue-item and attempt transitions; bounded
retry delays and error classification; declaration-ordered routing; and
shared, per-event, and templated session resolution. Scripted cases cover
idempotent ingress, fan-out and unhandled routing, fencing, retries,
cancellation, atomic completion, waits, deferred publications, session reads,
effects, and projection recovery. It contains no Python class names, timestamps
generated at runtime, or storage representation.

## `scheduling/runtime.json`

Implementation-neutral recurring-scheduler rules generated by the Python
harness and consumed by both host implementations. The cases pin default
same-day backfill, cross-day catch-up activation, missed and skipped decisions,
ordinary authored occurrence events, named timezones, disabled schedules,
pending and published status, and Europe/Paris DST gap/fold behavior. They keep
calendar policy in the host without introducing it into Dispatch.
